Full MSSQL support needs a database boundary across the engine. A dialect picker alone would leave PostgreSQL execution, transaction, metadata, and assistant assumptions intact.

The current flow is `Engine::console_run` → Rust statement splitting/classification → lazy tab session → session moved into `run_task` → prepare for metadata → text-row streaming into `ResultSet` → paged IPC reads. Preserve exclusive session ownership, database-scoped catalogs, UTF-16 offsets, and revisioned snapshots. Essential PostgreSQL coupling:

- **Connection configuration.** Neither saved connections nor drafts identify a database kind or dialect. Parsing uses `tokio_postgres::Config`, defaults to PostgreSQL credentials/database/port, and implements libpq SSL modes. - **Sessions and cancellation.** `Session` exposes a PostgreSQL `Client`, backend PID, notices, and cancellation token. Initialization runs `SET TimeZone`, `SET search_path`, and PostgreSQL server-info queries. Cancellation recognition depends on SQLSTATE `57014`; connection loss also checks PostgreSQL `FATAL`. See [session.rs:13](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/session.rs:13) and [console.rs:349](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/console.rs:349).

- **Results and values.** Preparation determines one result shape before execution. Streaming ignores subsequent metadata/completion messages. `StmtStatus` represents one result per statement. Column metadata exposes `PgTypeRef`, OIDs, and attribute numbers. MSSQL needs explicit batch/result-set events and adapter-owned text conversion, preserving `string | null` and precision. See [console.rs:312](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/console.rs:312), [console.rs:514](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/console.rs:514), and [model.rs:622](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/model.rs:622).

- **SQL interpretation.** Splitting, classification, formatting, relation extraction, history classification, and assistant vetting share PostgreSQL rules. Brackets are punctuation; `BEGIN` means transaction start and `END` means commit. Outline and formatting IPC receive no dialect. See [sql/lex.rs:81](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/sql/lex.rs:81), [sql/classify.rs:48](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/sql/classify.rs:48), and [ipc.rs:100](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/src-tauri/src/ipc.rs:100). [Microsoft variable-scope documentation](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/variables-transact-sql?view=sql-server-ver16).

- **Transactions and edits.** `txn_after` assumes any error in an active transaction aborts it. Close protection probes `pg_current_xact_id_if_assigned()`. Staged edits require complete primary keys and exactly one affected row, but use PostgreSQL savepoint syntax and restore `Active` even when undo fails. See [txn.rs:13](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/txn.rs:13), [lib.rs:510](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/lib.rs:510), and [lib.rs:1072](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/lib.rs:1072). MSSQL state must account for committability and nesting rather than reuse this reducer. [Microsoft transaction-state documentation](https://learn.microsoft.com/en-us/sql/t-sql/functions/xact-state-transact-sql?view=sql-server-ver17).

- **Metadata.** Database discovery, access checks, schema defaults/system classification, relations, estimates, types, routines, constraints, indexes, defaults, and triggers all query PostgreSQL catalogs. Detail loading also parses PostgreSQL-generated definitions. See [catalog.rs:21](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/catalog.rs:21), [detail.rs:8](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/detail.rs:8), and [view.rs:191](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/view.rs:191).

These builders must belong to the selected dialect, including count decoding and value round trips. See [text.rs:180](/Users/nallen/.t3/worktrees/L1Data/t3-a0f42d3d/crates/engine/src/text.rs:180).

- **Assistant safety.** Policy uses a PostgreSQL function/operator allowlist. Execution relies on PostgreSQL Parse to reject multiple statements and a fresh READ ONLY transaction with local timeouts. Prompts/context name PostgreSQL and recommend `LIMIT`; SQL fences recognize only generic/PostgreSQL labels. Preserve approval rechecking and dedicated sessions. MSSQL execution needs proven server-enforced protection before enabling it. Applying Boundary Discipline, my minimal safe recommendation is one engine-owned database module with PostgreSQL and SQL Server implementations. Hide driver clients, errors, types, cancellation, transaction commands/state, metadata queries, and value conversion behind it. Expose streamed result-set/row/completion/notice events. Keep pure dialect operations for batching, formatting, classification, quoting, browsing, edits, and assistant vetting.

Persist a per-connection backend selection that resolves its dialect everywhere. Existing JSON must default to PostgreSQL through handwritten deserialization. Backend changes must reset connected instances and tab sessions safely; saving currently only updates storage. Use neutral object/type/source identifiers scoped by `DatabaseRef`, and preserve unknown provenance as absent.
